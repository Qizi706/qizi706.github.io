## 1. Aside: 请求链路清楚以后，为什么系统还是会变慢？

阶段 1 的[《LLM 推理系统从请求到返回的完整链路》](/blog/llm-inference-request-lifecycle/)回答了一条请求怎样经过 Tokenizer、Scheduler、Prefill、KV Cache 与 Decode。

但知道组件名称，并不等于能够解释性能。

<SlideCard title="同一个模型，为什么会出现不同的性能？">

## Prompt 变长

- Prefill 需要处理更多输入 token
- 初始 KV Cache 变大
- Decode 每一步读取的历史状态也变多

## 并发增加

- 更多 Sequence 可以共同分摊权重读取
- Scheduler 每轮要在更多请求之间分配计算机会
- Queue、KV Cache 与尾延迟开始相互影响

## 调度策略改变

- 吞吐可能提高，但首 token 或 token 间延迟可能恶化
- 长 Prefill 可能阻塞正在 Decode 的请求
- Cache 容量不足时，请求可能等待、抢占或重算

</SlideCard>

<SlideCard title="只问“哪个优化更快”还不够">

## 常见答案

- 开启 FlashAttention
- 使用 PagedAttention
- 增大 Batch
- 启用 Prefix Cache
- 使用量化或 Speculative Decoding

## 真正需要先回答的问题

- 时间花在 Prefill、Decode、排队还是数据传输？
- 当前受限于计算、带宽、容量还是调度？
- 优化消除了哪一种浪费，又引入了什么成本？
- 瓶颈被消除以后，会转移到哪里？

</SlideCard>

<Note title="从请求地图转向资源地图" class="title-underline">

阶段 2 不再把推理优化理解成一组可以同时打开的开关，而是追踪一条因果链：**工作负载怎样改变计算和状态，Scheduler 怎样安排这些工作，最终又怎样反映到吞吐与延迟。**

本文只建立机制模型。最小 Attention 实现、原始计时数据和实验失败记录见[《LLM 推理性能实验：KV Cache、预分配与 Batched Decode》](/blog/vllm-inference-performance-lab/)；真实 vLLM Serving 是阶段 2 后半段的主要任务，不能用当前 Toy Lab 的结果替代。

</Note>

## 2. 从一次请求到三种性能状态

### 2.1 Prefill、Decode 与 Online Serving

<SlideCard title="同一份模型，三种不同的性能问题">

## Prefill

- 完整 Prompt 已知，可以同时处理多个输入位置
- 主要计算更接近 Matrix-Matrix Multiplication
- 输入长度与 Prefill Batch 共同影响计算效率
- 结果是首个输出 token，以及每一层的初始 K/V

## Decode

- 单个 Sequence 每轮只能确定一个新 token
- 每轮读取模型权重和不断增长的历史 K/V
- 小 Batch 下通常更难充分利用计算单元
- 结果是新 token，以及追加到 Cache 的新 K/V

## Online Serving

- 请求到达时间、Prompt 长度和生成长度都不固定
- Prefill 与 Decode 竞争同一设备和调度预算
- 吞吐、TTFT、TPOT、公平性与 KV 容量相互制约

</SlideCard>

“Prefill 计算密集、Decode 带宽受限”是一种常见工作区间下的性能倾向，而不是脱离 Batch、长度、模型和硬件的定律。短 Prompt 的 Prefill 也可能无法打满计算单元；Decode Batch 增大后，权重读取可以被更多 Sequence 分摊，瓶颈也可能移动。

<Note title="性能结论必须带条件" class="title-underline">

看到“Prefill 是 compute-bound”或“Decode 是 memory-bound”以后，还要继续追问：**在哪个模型、什么 Batch、什么长度、哪种硬件和哪个推理引擎上？** 最终结论应由工作负载与 Profiling 证明，而不是由一句经验判断代替。

</Note>

### 2.2 四类约束怎样连接？

<SlideCard title="推理性能的四种约束">

## Compute

- Q/K/V、MLP 与输出层需要多少运算
- Batch 和 Tensor Shape 能否提高设备利用率

## Bandwidth

- 权重、KV Cache 与中间结果需要搬运多少字节
- 每轮 Decode 的有效算术强度有多高

## Capacity

- 权重、KV Cache、Runtime Buffer 与 Workspace 能否同时放下
- 活跃 Sequence 增长后还剩多少可分配 Block

## Scheduling

- 哪些请求在本轮运行
- Prefill 与 Decode 怎样共享 Token Budget
- 等待、抢占、取消与释放怎样改变后续请求

</SlideCard>

这四类约束不是互斥标签。KV Cache 用容量换掉历史重算，却让 Decode 持续读取更多状态；Batching 提高设备利用率，却会增加请求竞争；PagedAttention 降低物理空间浪费，却不会让每个有效 token 的逻辑 K/V 消失。

## 3. KV Cache：从计算优化变成状态管理

### 3.1 它复用了什么？

在第 $l$ 层，位置 $i$ 的隐藏状态经过线性投影得到：

$$
K_i^{(l)} = h_i^{(l)}W_K^{(l)}, \qquad
V_i^{(l)} = h_i^{(l)}W_V^{(l)}.
$$

计算当前位置 $t$ 时，Dense Causal Attention 仍需要让新的 Query 与全部历史 Key 计算相关性，再聚合全部 Value：

$$
O_t^{(l)} = \operatorname{softmax}\left(
\frac{Q_t^{(l)}(K_{1:t}^{(l)})^T}{\sqrt{d_h}}
\right)V_{1:t}^{(l)}.
$$

历史 token 已经确定，所以同一层中的历史 K/V 在后续 Decode 中不会改变。KV Cache 利用的就是这个不变量。

<SlideCard title="一次 Decode Step 中，状态怎样变化？">

```text
Prefill finishes
  cache = K/V of prompt tokens [1, P]

Decode step t
  input:   latest accepted token
  read:    cached K/V [1, P + t - 1]
  compute: Q/K/V for the new position
  write:   append new K/V to cache
  output:  logits -> sample next token

Next engine step
  scheduler decides when this sequence runs again
```

</SlideCard>

没有 KV Cache 时，第 $t$ 轮 Decode 必须重新处理 Prompt 与此前生成的 token，历史位置的 Q/K/V、Attention 和 MLP 都会重复执行。有了 Cache，每轮只为最新位置计算新的 Transformer 状态。

但“复用”不等于“不再访问”。新的 Query 仍然需要读取全部历史 K/V。因此 KV Cache 消除了**历史状态的重复计算**，同时把问题转化为**容量、带宽和生命周期管理**。

### 3.2 每个 token 占多少 Cache？

对常见 Decoder-only Transformer，一个 token 的逻辑 KV Cache 大小可以近似写成：

$$
S_{\mathrm{KV/token}}
= 2 \times L \times H_{\mathrm{KV}} \times D_h \times B.
$$

- $2$：Key 与 Value 两份状态；
- $L$：Transformer Layer 数；
- $H_{\mathrm{KV}}$：Key/Value Head 数；
- $D_h$：每个 Head 的维度；
- $B$：每个缓存元素的字节数。

真实 Serving 中的活跃请求长度不同，因此总量更接近：

$$
S_{\mathrm{KV,total}}
\approx S_{\mathrm{KV/token}} \times
\sum_{r \in \mathrm{active}} T_r.
$$

<SlideCard title="容量公式告诉了我们什么？">

## 模型结构决定每 token 成本

- MHA 通常让每个 Query Head 拥有对应的 K/V Head
- MQA 让所有 Query Head 共享一组 K/V
- GQA 让一组 Query Head 共享一组 K/V

## 工作负载决定状态总量

- Prompt 越长，Prefill 后的初始 Cache 越大
- 输出越长，Decode 期间追加的 Cache 越多
- 活跃请求越多，同时驻留的 token 越多

## Runtime 决定物理可用量

- Block 对齐和最后一个未填满的 Block 会带来内部浪费
- Allocator、CUDA Graph、Workspace 与激活也需要空间
- “总显存减权重”不能直接当作可用 KV 容量

</SlideCard>

<Note title="逻辑容量不等于运行时占用" class="title-underline">

公式适合建立容量直觉，但 vLLM 真正能分配多少 KV Block，必须从固定版本和启动配置的运行时证据中确认。逻辑 Tensor、Block 管理开销与设备整体内存占用是三个不同层次。

</Note>

### 3.3 用最小实现验证不变量

为了不只停留在公式，我先用 NumPy 实现三条单 Sequence 的单头 Causal Attention 路径，再增加一个 `B=2` 的 Batched Decode 路径：

<SlideCard title="Toy Attention 的三条路径">

## No Cache

- 每一步对完整前缀重新计算 Q/K/V 与 Attention
- 只保留当前最后一个位置的输出

## Concatenate Cache

- 每一步只计算新 token 的 Q/K/V
- 使用 `np.concatenate` 扩展历史 K/V

## Preallocated Cache

- 预先分配完整 K/V Buffer
- 每一步原地写入新位置，只读取有效前缀

</SlideCard>

<SlideCard title="两个 Sequence 怎样组成 Batch？">

## Sequential Reference

- 在 Python 中分别执行两个等长 Sequence
- 两次调用共享同一套模型权重，但执行路径相互独立

## Batched Decode

- 输入 Shape 从 `[T, D_model]` 变为 `[B, T, D_model]`
- 每轮同时取出 `[B, 1, D_model]`
- 两个 Sequence 分别维护自己的 K/V，Attention 不跨越 Batch 维

</SlideCard>

三条 Cache 路径先通过逐 token 数值等价检查，Batched 路径再与两个独立 No-Cache 结果对照。测试刻意令 `d_k != d_v`，避免 K/V Shape 错误被相同维度掩盖；计时则固定 `d_model = d_k = d_v = 64`，比较动态拼接、预分配和两个 Sequence 的顺序/Batched 执行。

固定 OpenBLAS 与 OMP 为单线程后，`B=2` 的 Batched 路径比顺序执行快约 1.35–1.69x，但加速随 Sequence Length 增长而收窄。它减少的是 Python/NumPy 调用和分配次数，没有消除两个 Sequence 的 Attention 工作；当 $O(T^2)$ 的计算与动态 Cache 复制逐渐占主导，相对收益自然下降。

实验还暴露了一个重要问题：未固定 BLAS 线程时，No Cache 路径的矩阵计算跨过了不同执行策略阈值，导致表面加速比被放大。固定线程后趋势仍然存在，但具体倍数发生了变化。现在 Benchmark 会保留全部原始计时样本，不再只留下中位数。

完整代码、环境与边界保存在 [`attention-kv-caceh` Lab](/labs/attention-kv-caceh/README.md)。这个 Microbenchmark 只证明 Cache 复用与分配策略的最小机制，不代表真实 GPU Serving 的固定收益。

<Note title="机制验证不是 Serving Benchmark" class="title-underline">

当前实现只有 CPU、NumPy、单 Head、等长 Sequence、`B∈{1,2}` 和单层 Attention。这里的 Batch 只是固定形状的 Batched NumPy 执行，不包含请求到达、不同长度、动态加入/退出或 Token Budget，因此还不能回答 Multi-Head/GQA、GPU Kernel、Continuous Batching、PagedAttention 或真实 Scheduler 的性能问题。

</Note>

## 4. 推理优化不是同一层的开关

### 4.1 Model Architecture：改变必须保存的状态

<SlideCard title="MHA、MQA 与 GQA 改变了什么？">

## MHA

- Query Head 与 KV Head 数通常相同
- 表达能力直接，但每 token 的 K/V 状态更多

## MQA / GQA

- 多个 Query Head 共享一组或一组组 K/V
- 直接减少 $H_{\mathrm{KV}}$，因此降低 Cache 容量和相关读取字节数

## 边界

- 这是模型架构属性，不是任意模型都能无损打开的 Runtime 开关
- 容量计算应读取模型 `config.json`，不能只凭参数量猜测

</SlideCard>

权重量化、激活量化与 KV Cache 量化也作用于不同对象。它们都可能减少字节数，但精度代价、Kernel 支持与实际瓶颈并不相同。

### 4.2 Kernel / Runtime：改变相同语义怎样执行

<SlideCard title="FlashAttention 与 PagedAttention 不是一件事">

## FlashAttention

- 通过 Tiling 与算子融合改变 Attention 的执行顺序
- 减少中间结果在较慢内存层级之间的往返
- 优化的是 I/O 路径，不改变 Attention 的逻辑语义

## PagedAttention

- 把逻辑连续的 KV Cache 切成固定大小 Block
- 通过 Block Table 映射逻辑 token 位置与物理存储
- 减少过度预留、外部碎片和连续分配约束

## 两者都没有做到

- 不会自动减少每个有效 token 必须保存的逻辑 K/V
- 不保证所有模型、形状与硬件上得到相同收益

</SlideCard>

PagedAttention 与操作系统页表很像：上层看到连续空间，底层物理空间不必连续。但它首先解决的是设备侧 KV Block 的分配和寻址，并不意味着必须依靠 Page Fault，或一定把冷 Block 交换到磁盘。

### 4.3 Serving / Scheduler：改变请求怎样共享设备

Static Batching 中，已经完成的 Sequence 可能继续等待最长 Sequence，空出的执行槽不能及时接纳新请求。Continuous Batching 在迭代边界移除完成请求，并把新请求加入后续执行轮次，更适合长度动态的生成任务。

<SlideCard title="Continuous Batching 消除了什么？">

## 减少的浪费

- Batch 内等待最长 Sequence 的空槽
- 动态请求无法及时加入执行的问题
- 小 Batch 下权重读取难以摊薄的问题

## 新的竞争

- 更多请求竞争 Scheduler 的执行机会
- 活跃 Sequence 共同占用 KV Cache
- 到达率超过服务能力后，Queueing Delay 持续累积

## 最终权衡

- Token Throughput 可以提高
- TTFT、TPOT、公平性与 P99 不一定同时改善

</SlideCard>

## 5. “batch size”为什么不是一个数字？

在 LLM Serving 中，下面几个量经常被统称为 Batch Size，但它们表示不同状态：

<SlideCard title="四个不能混写成 batch size 的量">

## Client Concurrency

客户端同时尚未完成的请求数。

## Active Sequences

已经进入引擎、正在等待或运行，并保留状态的 Sequence 数。

## Sequence Batch

某一次 Engine Step 实际被 Scheduler 选中执行的 Sequence 集合。

## Token Budget

某次调度迭代允许处理的 token 总量；Prefill 请求可能一次消耗多个 token，Decode 请求通常只推进一个 token。

</SlideCard>

因此，改变 Client Concurrency 不等于直接设置模型执行 Batch；修改 `max_num_seqs` 或 `max_num_batched_tokens` 也不等于每一轮都会用满这些上限。真实 Sequence Batch 是请求状态、长度、KV 容量与调度策略共同形成的结果。

<Note title="标题可以简洁，实验变量必须精确" class="title-underline">

阶段 2 实验文章会在标题中使用更直观的 “batch size”，但实验记录会明确区分客户端负载、Scheduler 上限与每轮实际执行状态。否则“增大 Batch 后吞吐提高”无法说明究竟改变了什么。

</Note>

## 6. 从工作负载到用户指标

### 6.1 客户端看见什么？

<SlideCard title="Latency is still not one number">

## TTFT

$$
\mathrm{TTFT}=t_{\mathrm{first}}-t_{\mathrm{arrival}}
$$

包含客户端可见的排队、前端处理、Prefill 和传输时间。

## ITL 与 TPOT

$$
\mathrm{ITL}_i=t_i-t_{i-1}
$$

$$
\mathrm{TPOT}=\frac{t_{\mathrm{last}}-t_{\mathrm{first}}}{N_{\mathrm{output}}-1}
$$

描述首 token 以后，生成过程是否稳定流畅。

## E2E 与 Throughput

$$
\mathrm{E2E}=t_{\mathrm{finish}}-t_{\mathrm{arrival}}
$$

吞吐需要同时说明是 Request Throughput 还是 Token Throughput。

</SlideCard>

### 6.2 服务端发生了什么？

客户端时间只能告诉我“用户等待了多久”，不能独立证明时间花在 Scheduler、KV Cache 还是 Model Runner。解释因果关系还需要服务端证据：

- waiting / running requests；
- Queue Time 与 Scheduler 决策；
- 每轮调度的 Sequence 与 Token 数；
- KV Cache Usage、Block 分配、复用与释放；
- Model Execution、Prefix Cache 命中和失败状态。

<SlideCard title="一条需要被证据填满的性能链">

```text
request rate / client concurrency
  -> waiting and active sequences
  -> scheduler selects sequences and token budget
  -> KV blocks lookup / allocate / grow / release
  -> prefill and decode execute
  -> stream chunks return to client
  -> TTFT / ITL / TPOT / E2E / throughput / P99
```

每一个箭头都可能包含替代解释。只有客户端时序而没有服务端状态时，结论应该停留在“观测到相关变化”，不能直接声称某个 Scheduler 分支导致了结果。

</SlideCard>

## 7. 把机制模型变成可证伪实验

阶段 2 最终要回答：

> 在固定模型、推理引擎和硬件后，Input 长度、Client Concurrency 与 Scheduler Batch Budget 如何改变请求排队、KV Cache 占用和实际执行 Batch，并最终影响 TTFT、TPOT、Token Throughput 与尾延迟？

<SlideCard title="实验开始前先留下预测">

## Input Length

- 未命中 Prefix Cache 时，Prompt 变长应提高 TTFT 与初始 KV 占用
- 历史上下文增长还可能提高 Decode 的单步读取成本

## Client Concurrency

- Token Throughput 预计先提高，再接近饱和
- 越过容量点后，TTFT、TPOT 或 P99 可能继续恶化

## Scheduler Batch Budget

- 增大预算可能让单轮处理更多 token 或 Sequence
- 收益取决于工作负载是否真的能填满预算，以及 KV 容量是否允许

## Mixed Workload

- 长 Prefill 可能干扰已有 Decode 的 ITL
- 若 Chunked Prefill 或其他策略生效，这个干扰可能减弱或不可见

</SlideCard>

这些预测不是本文的结论。实验必须预先固定环境、模型、负载生成方式、Warm-up、重复次数和聚合方法，并把结果标记为 `Supported`、`Refuted` 或 `Inconclusive`。

<Note title="学习文章与实验文章的边界" class="title-underline">

本文负责解释为什么这些预测值得检验；[阶段 2 实验文章](/blog/vllm-inference-performance-lab/)负责记录当前 Toy Attention 实验支持了什么、证据边界在哪里，以及迁移到真实 vLLM 前还缺什么。后续 Serving 实验仍必须保留原始 CSV/JSON、启动配置、版本、日志、异常请求和复现命令，不能用理论预期替代尚未出现的数据。

</Note>

## 8. 阶段 2 剩余学习路线

### 8.1 当前已经跨过哪一道门？

现在已经不只是“读过 KV Cache 和 Batch”：我实现了 No Cache、Dynamic Cache、Preallocated Cache 与固定形状的 Batched Decode，用数值 Oracle 约束正确性，保留了原始计时样本，还定位并修正了 BLAS 线程造成的异常结果。

这意味着最小机制学习已经形成一次完整闭环：

```text
概念模型
  -> 自己实现
  -> 正确性验证
  -> 受控测量
  -> 异常诊断
  -> 修正结论边界
```

当前真正的能力缺口，是把这套方法迁移到一个**会排队、会饱和、会消耗 KV 容量，并由 Scheduler 动态形成 Batch** 的系统。继续给 NumPy Toy 增加完整 Transformer、MLP 或采样器，新增代码很多，却不会直接回答这个缺口。

### 8.2 为什么要按这个顺序推进？

<SlideCard title="阶段 2 的知识依赖链">

```text
固定 B=2 的 Batched Decode
  -> Batch Size 曲线：吞吐何时不再线性增长？
  -> MHA/GQA：一个 Sequence 究竟携带多少 KV 状态？
  -> Serving 可观测性：客户端指标能否和服务端状态对齐？
  -> 受控变量实验：长度、并发、调度预算、混合负载、前缀复用
  -> 固定版本源码追踪：观测到的拐点由哪条状态转换产生？
  -> 综合：Toy 预测在哪些地方成立，在哪些地方失效？
```

</SlideCard>

Batch Size 曲线先补齐“计算怎样随更多 Sequence 扩展”；MHA/GQA 再补齐“状态怎样随 Head 结构扩展”。有了这两个局部模型，进入 vLLM 后才知道应该观察什么。反过来，如果一开始只压并发，吞吐变化可能同时来自客户端排队、实际执行 Batch、KV 容量和 Backend 实现，无法归因。

### 8.3 四道学习门

| Gate    | 核心问题                                 | 必须留下的证据                                                 | 通过条件                                           |
| ------- | ---------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------- |
| M：机制 | Batch 和 KV Head 怎样改变计算与状态？    | `B=1/2/4/8` 原始样本；MHA/GQA 正确性测试与字节公式             | 能解释吞吐曲线，并让实际 `nbytes` 与公式一致       |
| O：观测 | 当前 vLLM Metal 到底支持哪些参数与指标？ | 版本、模型 Revision、完整启动命令、Capability Matrix、稳态基线 | 同一工作负载可复跑，客户端时间线能与服务端时间对齐 |
| E：实验 | 长度、并发和调度怎样共同形成瓶颈？       | 每请求 JSON、服务端 Metrics、配置快照、汇总表与异常记录        | 找到饱和拐点，并复现至少一次延迟代价或资源约束     |
| R：因果 | 指标变化对应源码中的哪条状态转换？       | 固定 Commit 的调用链、请求状态机、关键不变量                   | 能用源码解释一次实测现象，并指出至少一个替代解释   |

Gate 是依赖，不只是日历进度。前一道门没有通过时，应修复实验设计或降低结论强度，而不是继续叠加更多变量。

## Week 3：制造饱和

- 固定实际运行版本追踪 Scheduler、KV Cache 与 Model Runner
- 回写两篇文章，接受独立复跑或第二套聚合结果的反馈

### 8.5 阶段 2 的停止条件

阶段 2 不是以“看完 vLLM 源码”或“跑出最高吞吐”为完成标准。它至少需要满足：

1. Toy Lab 的 Batch 与 MHA/GQA 两项机制实验通过正确性门禁；
2. 真实 Serving 环境和能力边界可以从产物中复现；
3. Input Length、Client Concurrency、Scheduler Budget 至少各有一组受控实验；
4. Mixed Workload 或 Prefix Reuse 至少复现一个系统级现象；
5. 用固定版本源码解释一个实测现象，并记录 Toy 预测与真实系统之间至少一个不一致；
6. 所有结论都能回到原始数据、配置和日志，而不是只剩图表或平均数。

每一个未出现预期效果的实验也可以成为有效产出，但必须标记为 `Inconclusive` 或 `Refuted`，并说明缺失的是能力、观测还是机制证据。具体执行契约放在[阶段 2 实验文章](/blog/vllm-inference-performance-lab/)中。

## 9. 重新回答最初的问题

<SlideCard title="一个请求为什么会变慢？">

## 它可能在等待

- 到达率超过服务能力
- Scheduler 优先处理其他 Sequence
- KV Cache 暂时没有可用 Block

## 它可能在执行更多工作

- Prompt 更长，Prefill 计算增加
- 输出更长，Decode 轮数增加
- Cache 未命中导致重复计算

## 它可能在搬运更多状态

- 历史上下文增长，每一步读取更多 K/V
- Batch、Head 数或数据类型改变了字节量
- Runtime 的内存层级与 Kernel 没有高效承载这些访问

</SlideCard>

<SlideCard title="阶段 2 最后应该留下什么理解？">

## KV Cache

用容量换掉历史重算，同时带来持续读取和生命周期管理问题。

## PagedAttention

改善物理 KV 空间的分配与复用，不改变每个有效 token 的逻辑状态量。

## Continuous Batching

让动态请求更有效地共享设备，但需要在吞吐、延迟、公平性与容量之间取舍。

## Benchmark

不是寻找一个最大数字，而是用受控工作负载判断瓶颈位于哪里，以及优化后它转移到了哪里。

</SlideCard>

<Note title="阶段 2 的核心问题" class="title-underline">

判断一项推理优化是否有效，最终要回答三件事：**它消除了哪一种浪费，引入了什么新成本，以及原来的瓶颈被转移到了哪里。**

</Note>
