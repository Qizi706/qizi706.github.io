## 怎么用这些卡片

- 一张卡片只回答一个问题，答案分三层：一句话结论、机制、证据，再加上面试官可能的追问。
- 卡片按学习顺序排列，和计划里每周的体系结构线对应；C++ 语言本身的卡片在[C++ 八股卡片](/blog/cpp-interview-cards/)。
- 复习时先只看问题和要点，口头答完再展开对照。能答到“到底层”那一层才算过。
- 答不上来的卡片，在标题后面加上“（卡住过）”，下次复习时优先看。
- 卡片 1–6 的实测来自[存储器层次与 cache](/blog/memory-hierarchy-cache-locality/)第 8 节，只在 Apple clang 21、Apple M5 Pro 上测过；性能数字离开这台机器不能直接套用。

## 存储器层次与 cache

### 1. 为什么按列遍历二维数组比按行慢？

要点：一次缺失搬上来一整个 line；按行步长为 1，按列每次跳一整行；缺失次数之比不等于耗时之比；本机实测约 59 倍。

<details>
<summary>展开答案</summary>

- **一句话**：二维数组按行优先存放，按行走时相邻访问只差 4 字节，一个 128 字节的 line 能用上 32 个 `int`；按列走时每次跳一整行，每次访问都落在新的 line 上，等回来读下一列时，这些 line 往往已经被挤出去了。两者复杂度相同，差距全在访问顺序。
- **往下一层**：用步长估算每次访问的缺失。设一个 line 装 L 个元素，步长为 1 时缺失约 1/L，步长达到一个 line 后每次都缺失。本机 `int` 的 L = 32，所以模型给出的缺失次数之比约 32 倍。平均访问时间 = 命中时间 + 缺失率 × 缺失代价，缺失代价比命中时间大两个数量级，所以要盯着缺失率看。
- **到底层**：N = 4096、`-O2` 下实测 `sum_cols` 54.0 ms、`sum_rows` 0.91 ms，约 59 倍，比 32 倍还大。缺失次数之比不等于耗时之比：预取和乱序执行会缩小差距；`sum_rows` 被向量化，达到约 74 GB/s，而 `sum_cols` 在 N = 4096 时还撞上冲突缺失（卡片 3），这两点又会放大差距。换成 `-O0`，比值降到约 3.4 倍，因为 `sum_rows` 变成受指令数限制，额外开销稀释了比值。
- **追问**：
  - `vector<Tick>` 顺序遍历只读 `price`，空间局部性好吗？按元素步长为 1，按字节每次跳 `sizeof(Tick)`，line 里只有一部分数据被用上。热点循环只读少数字段时改成 SoA，读大部分字段时保留 AoS。
  - 矩阵只有 256 KiB 时差距会怎样？本机实测降到约 13 倍：数据装得进 L2，缺失代价从 DRAM 的量级降到 L2 的量级。
- **出处**：[存储器层次与 cache · 第 2、3、8 节](/blog/memory-hierarchy-cache-locality/)，CS:APP 第 6 章

</details>

### 2. 组相联 cache 怎么查找？地址怎么拆？

要点：C = S × E × B；地址拆成 tag、组索引、块内偏移；用中间位做组索引；相联度是冲突和电路代价的取舍。

<details>
<summary>展开答案</summary>

- **一句话**：cache 分成 S 组，每组 E 行，每行 B 字节，容量 C = S × E × B。查找时用地址的中间几位选组，再拿高位的 tag 和组里每一行比较，命中后用低位的偏移在 line 里取数据。
- **往下一层**：设 $B = 2^b$、$S = 2^s$，最低 b 位是块内偏移，中间 s 位是组索引，其余高位是 tag。例：64 KiB、8 路、128 字节 line，S = 65536 / (8 × 128) = 64，b = 7、s = 6。地址 `0x12345` 拆成偏移 `0x12345 & 0x7F = 69`、组 `(0x12345 >> 7) & 0x3F = 6`、tag `0x12345 >> 13 = 9`。缺失时把整块搬进这一组，组满了按近似 LRU 替换一行。
- **到底层**：用中间位而不是高位做组索引，是因为连续内存的高位相同，用高位会让一大段连续数据挤进同一组；用中间位，相邻的 line 落在相邻的组，顺序访问能铺满整个 cache。E = 1 是直接映射，S = 1 是全相联；E 越大冲突越少，但每次要并行比较更多 tag，面积、功耗和命中延迟都会上升，所以 L1、L2 都是组相联。macOS 不通过 `sysctl` 公开相联度，本机只能查到容量和 line 大小（128 字节）。
- **追问**：
  - 三类缺失分别怎么缓解？冷缺失靠预取；容量缺失靠缩小工作集，比如分块；冲突缺失靠改变地址分布，比如给每行加填充。
  - 写命中和写缺失怎么处理？现代数据 cache 一般是写回加写分配：只改 cache 并标记为脏，替换时才写回；写缺失时先把整块搬上来再写。所以只写不读的数组也会先被读进 cache。
- **出处**：[存储器层次与 cache · 第 4 节](/blog/memory-hierarchy-cache-locality/)，CS:APP 6.4

</details>

### 3. 为什么矩阵行宽是 2 的幂时按列访问特别慢？

要点：组索引按 C/E 字节循环；步长 d 是 2 的幂时一级 cache 只能容纳 C/d 个 line；N = 4096 → 4100，`sum_cols` 耗时降到约 40%；要逐级看。

<details>
<summary>展开答案</summary>

- **一句话**：行宽是 2 的幂时，同一列的地址每次加的步长正好是组索引周期的整数倍，全都映射到少数几个组里，cache 整体没满也在互相挤，这是冲突缺失。
- **往下一层**：组索引每隔 $S \times B = C / E$ 字节绕回一次。步长 d 是 2 的幂且 $B \le d \le C / E$ 时，一串访问只能用到 $(C / E) / d$ 个组，每组 E 行，能容纳的 line 数是 $C / d$，相联度被约掉了。N = 4096 的 `int` 矩阵行宽 16 KiB，本机 16 MiB 的 L2 只能容纳 1024 个 line，而一列有 4096 个，下一列只能回 DRAM 取。
- **到底层**：实测 `-O2` 下 `sum_cols` 在 N = 4096、4100、4128 时分别是 54.0、20.7、22.4 ms。N = 4100 时每行多 16 字节，要 8 行才让组索引加 1，一列分散到 L2 的许多组，下一列多数在 L2 命中。注意 L1 不是差别所在：一列 512 KiB，两种 N 都装不进 128 KiB 的 L1。这个推导假设组索引直接取地址中间位，硬件若对索引做哈希，具体数字会不同。
- **追问**：
  - 怎么修？让行宽不是 2 的幂：分配时每行多留几个元素（padding），下标仍用 `i * ld + j`，`ld` 是填充后的行宽。
  - N = 256 时按列访问还会冲突吗？行宽 1 KiB，128 KiB 的 L1 只能容纳 128 个 line，少于一列的 256 个，所以每次访问都要去 L2；但 256 KiB 的矩阵整体装得进 L2，差距从 59 倍降到约 13 倍。
- **出处**：[存储器层次与 cache · 第 4、8 节](/blog/memory-hierarchy-cache-locality/)

</details>

### 4. 矩阵乘法的 6 种循环顺序，哪种最快？

要点：只看最内层循环；第二个下标随内层变 → 1/L，第一个下标随内层变 → 1，不随内层变 → 0；ikj、kij 最好，约 2/L；jki、kji 最差，约 2。

<details>
<summary>展开答案</summary>

- **一句话**：ikj 和 kij 最快。它们的内层循环沿着 B 和 C 的同一行走，两者步长都是 1；A 的元素在内层不变，可以放进寄存器。
- **往下一层**：`n × n` 的 `double` 矩阵，本机一个 line 装 L = 16 个，n 大到一列装不进 cache 时，估算每次内层迭代的缺失：

  | 循环顺序 | 内层访问 | 缺失 | L = 16 |
  | --- | --- | --- | --- |
  | ijk、jik | A 按行，B 按列 | 1 + 1/L | 约 1.06 |
  | jki、kji | A 按列，C 按列 | 2 | 2 |
  | kij、ikj | B 按行，C 按行 | 2/L | 0.125 |

  判断方法：看内层循环变量出现在每个矩阵下标的哪个位置。
- **到底层**：ikj 的写法是 `r = A[i*n+k]` 提到最内层外面，`for j: C[i*n+j] += r * B[k*n+j]`，内层是连续的乘加，也容易被向量化。最好和最差在模型上差 16 倍，这是估算，没有考虑预取和多级 cache，本机还没有实测。
- **追问**：
  - 再往上怎么优化？分块：把矩阵切成装得进 cache 的小块，在一块上算完再换下一块，让时间局部性也用足。
  - ijk 的 C 为什么不算缺失？`C[i][j]` 在内层不变，可以用一个寄存器累加，内层结束再写回。
- **出处**：[存储器层次与 cache · 第 5 节](/blog/memory-hierarchy-cache-locality/)，CS:APP 6.6.2

</details>

### 5. 什么是 false sharing？怎样避免？

要点：一致性以 line 为单位；两个线程写不同变量，但变量在同一个 line 上；line 在核之间来回传递；`alignas` 按目标机器的 line 大小隔开，本机是 128。

<details>
<summary>展开答案</summary>

- **一句话**：两个线程写的是不同变量，逻辑上没有共享，但变量落在同一个 cache line 上。一致性协议以 line 为单位，一个核写之前要让别的核的副本失效，于是这个 line 在两个核之间来回搬，本该并行的代码可能比单线程还慢。
- **往下一层**：解决办法是让它们落在不同的 line 上：

  ```cpp
  struct Counters {
      alignas(128) std::atomic<long long> a;
      alignas(128) std::atomic<long long> b;
  };
  ```

  本机的 line 是 128 字节，很多资料按 x86 的 64 字节写，搬到这台机器上不够。
- **到底层**：`std::hardware_destructive_interference_size` 是编译期常量，本机 Apple clang 21 和 GCC 16 下都是 256，比实际的 128 大，能保证隔开，代价是多占空间。它是编译期的保守值，不一定等于运行时机器的 line 大小。写分配也起作用：即使只写不读，写一个变量也要先拿到整个 line 的独占权。
- **追问**：
  - 低延迟系统里哪里常见？各线程分别更新的统计计数器，SPSC 队列的 head 和 tail。SPSC 队列把 head、tail 分开对齐，还会各自缓存对端的索引，减少读对端 line 的次数。
  - 和 true sharing 的区别？true sharing 是确实在读写同一个变量，只能靠减少共享来解决，加对齐没用。
- **出处**：[存储器层次与 cache · 第 6 节](/blog/memory-hierarchy-cache-locality/)，[cppreference：hardware_destructive_interference_size](https://en.cppreference.com/w/cpp/thread/hardware_destructive_interference_size)

</details>

### 6. 怎样可靠地测一段只要几微秒的代码？

要点：结果要用掉但打印放在计时外；先预热；重复上千次取平均，多次运行取最小值或中位数；防止编译器合并重复调用；交代机器、编译器和选项。

<details>
<summary>展开答案</summary>

- **一句话**：单次耗时和计时噪声一样大时，测出来的是噪声。要先预热，再在计时区间里重复调用上千次取平均，并确保编译器既没删掉计算，也没把多次调用合并成一次。
- **往下一层**：
  - 结果要用掉，否则 `-O2` 可能把整个循环删掉；但打印要放在计时区间外，终端里每次 `printf` 是一次系统调用，要几微秒。
  - 预热让 CPU 升频、数据进入 cache、页表建好。
  - 输入不变时，编译器可能只算一次再复用。每次调用前加屏障 `asm volatile("" : : "r"(p) : "memory");`，告诉编译器 p 指向的内存可能被改过。Google Benchmark 的 `DoNotOptimize` 和 `ClobberMemory` 是同样的思路。
  - 一次运行内多次取最小值，去掉偶发干扰；多次运行取中位数，看稳定性。
- **到底层**：N = 256 的按行和按列求和，第一版把 `printf` 包在计时区间里，测出约 6.6 倍；移出打印、预热 1000 次、再重复 1000 次取平均后，5 次运行稳定在约 13 倍（rows 约 3.0 µs，cols 约 38.7 µs）。打印给两边各加了几微秒，把比值压低了。
- **追问**：
  - 用 `-O0` 测性能可以吗？不行，`-O0` 的瓶颈和发布版本不同，`-O0` 下按行和按列的比值只有约 3.4 倍，结论会被带偏。
  - 结论要附带什么？机器、编译器版本、编译选项和输入规模，性能数字离开这些信息就没有意义。
- **出处**：[存储器层次与 cache · 第 8 节](/blog/memory-hierarchy-cache-locality/)，[Google Benchmark 用户指南](https://github.com/google/benchmark/blob/main/docs/user_guide.md)

</details>
