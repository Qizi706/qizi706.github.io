## 1. Aside：KV Cache 和 Batch 为什么会更快？

<SlideCard title="两个看似显然的优化">

## KV Cache

- 历史 token 的 K/V 已经确定，不必在每轮 Decode 中重新生成；
- 只计算新位置的 Q/K/V，再让新 Query 读取历史 K/V；
- 因而 Cache 路径应该比完整前缀重算更快。

## Batch

- 两个 Sequence 不再分别调用同一套 Attention；
- 每个 Decode Step 用一次 NumPy 调用同时推进两个位置；
- 因而 Batched 执行应该比顺序执行两次更快。

## 但“更快”还不是解释

> 优化究竟消除了哪一部分工作？为什么收益会随 Sequence Length 改变？它能否迁移到真实 LLM Serving？

</SlideCard>

<Note title="先说明实验边界" class="title-underline">

这不是 vLLM、GPU 或在线 Serving Benchmark，而是进入真实系统实验前的机制验证。实验只覆盖 CPU、NumPy、单 Head、等长 Sequence 和固定 Batch。它能证明最小实现中的数值不变量与耗时趋势，不能直接给出 vLLM 的 TTFT、TPOT、吞吐或 P99。

机制背景见[《LLM 推理优化的系统视角：从 KV Cache 到调度》](/blog/llm-inference-optimization-system-view/)，完整代码与原始数据见 [`kv-cache-batch` 实验产物目录](/labs/kv-cache-batch/)。

</Note>

<Note title="截至 2026-08-18 的进度" class="title-underline">

- M0 已实现 Cache、预分配和固定 <code>B=2</code> 的 Batched Decode；当前公开归档保留 300 条 Batch Length 原始样本，但 Cache Strategy 只保留汇总值，存在逐样本证据缺口。
- M1 已完成 <code>B=1/2/4/8</code> 正确性检查、240 条原始样本、P50/P95 汇总、两张独立曲线和 Knee 判定。
- Python/NumPy 语义练习代码已经覆盖 Binding、View/Copy、Advanced Indexing、<code>swapaxes</code> 与 <code>concatenate</code>，但还没有保存事前预测和运行后反思，因此 P0 仍是 In progress。
- M2 的 MHA/GQA 与 KV 容量实现尚未开始；当前下一步是先关闭 P0 验收，再进入 Head 维度与容量实验。

</Note>

## 2. 实验问题与事前预测

### 2.1 五个问题

1. 增量 KV Cache 与每步重算完整前缀是否逐位置数值等价？
2. 动态扩展 Cache 时，反复执行 <code>np.concatenate</code> 带来了多少额外成本？
3. 把两个独立 Sequence 放入 <code>B=2</code> 的执行路径后，总耗时是否低于顺序执行两次？
4. Sequence 变长时，Batch 的相对收益为什么可能收窄？
5. 固定 <code>T=128</code> 后，Batch Size 从 1 增加到 8 时，吞吐收益何时开始收窄？

### 2.2 实验前冻结的预测

**H1 / 语义不变：** Dynamic Cache、Preallocated Cache 与 No Cache 的逐位置输出应在浮点容差内一致。

**H2 / 分配成本：** 预分配 K/V Buffer 应比逐步拼接更快，并且长度越大，累计分配与复制成本越容易显现。

**H3 / Batched 执行：** <code>B=2</code> 应减少 Python 循环、NumPy 调用和数组分配次数，所以总耗时应低于顺序执行两个 Sequence。

**H4 / 收益边界：** Batch 没有消除两个 Sequence 的 Attention 工作，因此加速不会稳定达到 2x；随着 $T$ 增长，真正的矩阵计算与 Cache 复制占比上升，相对收益可能下降。

**H5 / Batch Size 拐点：** Batch Wall Time 会随 B 增大，总 Positions/s 会先提高后进入平台；若相邻一级 B 的吞吐增幅低于 10%，就把该 B 记作当前工作负载下的 Knee。

结果只使用 <code>Supported</code>、<code>Refuted</code> 或 <code>Inconclusive</code>。这里的 <code>Supported</code> 只表示当前环境和扫描范围支持预测，不表示它已经成为跨 Runtime、硬件和模型的普遍结论。

## 3. 实现：从单 Sequence Cache 到两个 Sequence

### 3.1 三条 Cache 路径

<SlideCard title="同一语义，三种执行方式">

## No Cache

- 第 $t$ 步取出 <code>x[:t+1]</code>；
- 对完整前缀重新计算 Q/K/V 与 Causal Attention；
- 只保留最后一个位置的输出。

## Concatenate Cache

- 每一步只计算新 token 的 Q/K/V；
- 使用 <code>np.concatenate</code> 把新 K/V 追加到历史；
- 新 Query 仍然读取 $1\ldots t$ 的全部 K/V。

## Preallocated Cache

- 预先分配 <code>[T, D_k]</code> 与 <code>[T, D_v]</code> Buffer；
- 每步原地写入位置 $t$；
- Attention 只读取当前有效前缀。

</SlideCard>

No Cache 的外层 Decode 循环不断调用完整 Causal Attention。单次前缀 Attention 的 Score Matrix 随 $t^2$ 增长，把所有 Decode Step 累加后，核心工作接近 $O(T^3)$。

两条 Cache 路径每步只有一个新 Query 与 $t$ 个历史 Key 做 Attention，累计工作接近 $O(T^2)$。Dynamic Cache 还要反复复制逐渐增长的 K/V，Preallocated Cache 则用一次容量分配换掉这部分动态扩容。

### 3.2 两个 Sequence 怎样组成 Batch？

顺序路径在 Python 中分别执行两个 Sequence；Batched 路径把输入从 <code>[T, D_model]</code> 变成 <code>[B, T, D_model]</code>，然后在每个 Decode Step 同时取出 $B$ 个位置：

```python
x_t = x[:, t : t + 1, :]
```

当 <code>B=2</code> 时，核心 Shape 为：

| Tensor                | Shape                        | 含义                               |
| --------------------- | ---------------------------- | ---------------------------------- |
| <code>x_t</code>      | <code>[2, 1, D_model]</code> | 两个 Sequence 的当前位置           |
| <code>q_t</code>      | <code>[2, 1, D_k]</code>     | 两个互相独立的 Query               |
| <code>k_cache</code>  | <code>[2, t+1, D_k]</code>   | 每个 Sequence 自己的 Key 历史      |
| <code>scores</code>   | <code>[2, 1, t+1]</code>     | Batch 内分别计算的 Attention Score |
| <code>output_t</code> | <code>[2, 1, D_v]</code>     | 两个 Sequence 的当前位置输出       |

Batch 维只表示共享一次算子调用，不能参与 Sequence 内部的 Attention。实现通过

```python
q_t @ np.swapaxes(k_cache, -1, -2)
```

让每个 <code>q_t[b]</code> 只访问同一个 $b$ 下的 K/V；测试再把 Batched 输出与两个独立 No-Cache Oracle 对照，防止状态跨 Sequence 泄漏。

### 3.3 这个 Batch 还不是什么？

<SlideCard title="当前 B=2 与真实 Serving 的差别">

## 当前实验

- 两个请求同时开始；
- 两个 Sequence 等长；
- 每轮都共同推进一个位置；
- 没有中途加入、完成、取消或抢占。

## 真实 Serving

- Client Concurrency 只表示尚未完成的请求数；
- Scheduler 每轮重新选择实际运行的 Sequence；
- Prefill 可能一次占用多个 Token Budget；
- 长度、KV 容量和调度策略共同决定实际 Batch。

> 因此，本实验测到的是固定形状的 Batched Execution，不是 Continuous Batching。

</SlideCard>

## 5. 实验 A：KV Cache 与分配策略

<Note title="这一组结果的证据状态" class="title-underline">

下面保留的是 M0 当时记录的 30 次中位数和机制解释。实现与正确性单测仍然存在，但对应的 450 条 Cache Strategy 原始样本已经不在当前公开归档中，所以读者无法从现有文件独立重算这些中位数。它可以作为已完成实验的历史汇总，不能当作当前复现包中证据完整的一组结果。

</Note>

### 5.1 结果

| $T$ | No Cache / ms | Concatenate / ms | Preallocated / ms | No Cache / Preallocated |
| --: | ------------: | ---------------: | ----------------: | ----------------------: |
|  16 |         0.271 |            0.194 |             0.180 |                   1.51x |
|  32 |         0.567 |            0.307 |             0.282 |                   2.01x |
|  64 |         1.740 |            0.648 |             0.577 |                   3.02x |
| 128 |         7.765 |            1.366 |             1.174 |                   6.61x |
| 256 |        40.592 |            3.083 |             2.509 |                  16.18x |

表中每个值是当时 30 次正式运行的中位数。三条路径在所有长度上都通过逐位置数值等价检查；当前单元测试仍分别覆盖 Dynamic Cache 和 Preallocated Cache 与 No-Cache Oracle 的数值等价性。

### 5.2 结果怎样解释？

**H1 得到支持。** Cache 改变的是历史状态的复用方式，没有改变当前 Query 对有效历史 K/V 的 Attention 语义。

**H2 在历史测量中得到支持，但存在复现缺口。** 五个长度上，Preallocated 的中位数都低于 Concatenate。到 <code>T=256</code> 时，耗时从 3.083 ms 降到 2.509 ms，减少约 18.6%。在重新生成独立的 <code>results/cache-strategy/raw.csv</code> 之前，这个趋势不能从当前归档重新聚合或检查分布。

No Cache 与 Preallocated 的差距从 1.51x 扩大到 16.18x。这里不是 Cache 让 Attention 消失了，而是它不再对每个 Decode Step 的完整前缀重复构造 Q/K/V 和 Score Matrix。

本实验中单 Sequence 的逻辑 K/V 容量为：

$$
S_{KV}
= T \times D_k \times 8
+ T \times D_v \times 8.
$$

当 <code>D_k=D_v=64</code> 时：

$$
S_{KV}=2\times T\times64\times8
=1024T\ \text{bytes}
=T\ \text{KiB}.
$$

因此 <code>T=256</code> 时只保存 256 KiB K/V。这个公式验证了容量随 $T$ 线性增长，但它不包含模型层数、Multi-Head/GQA、Allocator 元数据或设备侧 Block。

## 6. 实验 B：顺序执行与 B=2

### 6.1 结果

| $T$ | Sequential / ms | Batch / ms | Speedup | Positions / s |
| --: | --------------: | ---------: | ------: | ------------: |
|  16 |           0.380 |      0.226 |  1.683x |       141,656 |
|  32 |           0.780 |      0.429 |  1.817x |       149,032 |
|  64 |           1.253 |      0.777 |  1.613x |       164,766 |
| 128 |           2.644 |      1.739 |  1.521x |       147,242 |
| 256 |           6.122 |      4.496 |  1.362x |       113,866 |

<code>Sequential / ms</code> 与 <code>Batch / ms</code> 都包含两个 Sequence 的完整
Decode。Sequential 和 Batched 两条路径都使用动态拼接 Cache，因此这里比较的是执行组织方式，不是“动态
Cache vs. 预分配 Cache”。

<code>Positions / s</code> 使用

$$
\frac{B\times T}{T_{\mathrm{batch}}}
$$

计算，只表示 Toy Attention 每秒处理多少个输出位置。它没有请求排队、Tokenizer、模型层、Sampling 或网络时间，不能称为真实 Serving 的 Token Throughput。

### 6.2 Batch 节省了什么？

**H3 得到支持。** 在五个长度上，Batched 总耗时都低于顺序执行两次。它把每个位置的两次 Python/NumPy 调用合并为一次，并减少了中间数组和函数调度开销。

**H4 得到有条件支持。** Speedup 并没有在全部五个点上单调下降：它从 <code>T=16</code> 的 1.683x 上升到 <code>T=32</code> 的 1.817x，随后才随长度增加逐步降到 <code>T=256</code> 的 1.362x。当前证据支持“中长 Sequence 中收益收窄”，不支持“从最短长度开始严格单调收窄”。

原因可以用工作量的增长速度解释：

```text
顺序路径：2 × T 次 Python Decode Step
Batched： T 次 Python Decode Step

节省的调用开销：大致随 T 增长
仍然存在的 Attention 与 Cache 工作：大致随 B × T² 增长
```

短 Sequence 的单次结果容易受函数调用、分配和亚毫秒噪声共同影响；从 <code>T=32</code> 到 <code>T=256</code>，Attention 与 Cache 复制逐渐主导，总计算没有减半，所以加速整体向 1x 收窄。

这个结果支持“Batch 能摊薄执行开销”，但还不能证明 GPU 利用率提高或模型权重带宽被更好地分摊：当前实现运行在 CPU/NumPy 上，也没有采集硬件计数器。

### 6.3 M1：固定 T 的 Batch Size Scan

固定 <code>T=128</code> 后，只改变 <code>B∈&#123;1,2,4,8&#125;</code>。每个 B 共用同一份最大输入的前缀、同一组权重和单线程 BLAS；Sequential 与 Batched 各保留 30 条原始计时样本。

| $B$ | Batch P50 / ms | Batch P95 / ms | P50/B / ms | Positions/s | Sequential/Batch |
| --: | -------------: | -------------: | ---------: | ----------: | ---------------: |
|   1 |          1.442 |          1.467 |      1.442 |      88,750 |           0.938x |
|   2 |          1.789 |          1.808 |      0.894 |     143,129 |           1.521x |
|   4 |          2.627 |          2.673 |      0.657 |     194,928 |           2.045x |
|   8 |          5.264 |          5.312 |      0.658 |     194,513 |           2.064x |

![Batch Size 对 Batch P50/P95 的影响](/labs/kv-cache-batch/results/batch-size-scan/batch-latency-percentiles.svg)

![Batch Size 对 Positions/s 的影响](/labs/kv-cache-batch/results/batch-size-scan/positions-throughput.svg)

相邻一级 B 的吞吐增幅由原始 CSV 计算：

| B 变化 | Positions/s Gain |
| -----: | ---------------: |
|  1 → 2 |           61.27% |
|  2 → 4 |           36.19% |
|  4 → 8 |           -0.21% |

操作性定义为相邻吞吐增幅低于 10% 时收益明显收窄，因此结果是 **Knee: B=8**，不是 <code>Not reached</code>。

Batch Wall Time 从 1.442 ms 增长到 5.264 ms，说明吞吐提高不等于整个 Batch 更快完成。<code>P50/B</code> 从 B=1 的 1.442 ms 降至 B=4 的 0.657 ms，但 B=8 时为 0.658 ms，摊销收益已经停止改善。Positions/s 同样在 B=4 后进入平台。

B=1 时 Sequential/Batch 为 0.938x，说明没有可摊薄的多 Sequence 调用时，Batched 形状处理本身存在开销；B≥2 后 Batched 才取得净收益。B=8 的 2.064x 仍远低于 8x，因为每个 Sequence 的 Q/K/V、Attention 与 Cache 工作都没有消失。

平台可能来自 CPU/NumPy 调用、内存访问和动态 Cache 复制共同占据主导，但当前实验没有硬件计数器，不能把 Knee 唯一归因于某一种机制。它也不是在线请求延迟或 Continuous Batching 的调度拐点。

## 7. 一次无效结果：为什么曾经出现 40x？

早期实验没有固定 BLAS 线程。随着矩阵 Shape 改变，OpenBLAS 可能跨过不同执行策略或线程阈值，No Cache 路径的额外调度成本被一起算进结果，表面加速一度超过 40x。

<SlideCard title="异常怎样变成实验约束？">

## Observation

No Cache 的加速比远高于机制模型能够解释的范围，并且复跑波动明显。

## Competing explanation

变化可能来自 BLAS 线程与执行策略，而不只是 KV Cache。

## Controlled change

固定 <code>OPENBLAS_NUM_THREADS=1</code> 与 <code>OMP_NUM_THREADS=1</code>，保持其他条件不变后重跑。

## New conclusion

Cache 趋势仍然存在，但具体倍数下降；因此旧的 40x 结果不能作为 KV Cache 的独立证据。

</SlideCard>

保留原始样本也暴露了中位数看不到的噪声。例如当前 <code>T=256</code> 的 Batched 路径中位数为 4.496 ms，但 30 次样本中的最大值达到 5.707 ms。报告中位数能够降低单次尖峰的影响，却不能替代原始分布、随机化顺序和更多环境观测。

## 8. 结果总览与证据边界

| 假设                   | 状态      | 当前证据                                     | 结论边界                      |
| ---------------------- | --------- | -------------------------------------------- | ----------------------------- |
| H1：Cache 保持语义     | Supported | 当前单测 + 历史逐长度 Oracle                 | 单层、单 Head、CPU/NumPy      |
| H2：预分配减少成本     | Supported | 历史中位数汇总；当前缺少 450 条逐样本数据    | 无法从公开归档重新聚合        |
| H3：B=2 快于顺序两次   | Supported | 独立 Oracle + 当前 300 条 Batch Length 样本  | 等长、同时开始、动态 Cache    |
| H4：中长 T 下收益收窄  | Supported | T=32 时 1.817x，T=256 时 1.362x              | 全部五个点并非严格单调        |
| H5：Batch 收益出现拐点 | Supported | 当前 240 条样本；gain(8)=-0.21%，Knee 为 B=8 | 固定 T=128、CPU/NumPy Toy Lab |

<Note title="这次实验真正证明了什么？" class="title-underline">

KV Cache 用线性增长的状态换掉了更昂贵的历史重算；预分配减少了动态扩容与复制；Batched 执行摊薄了调用开销，但没有消除每个 Sequence 的 Attention 工作。固定 <code>T=128</code> 时，Positions/s 在 B=4 后进入平台并于 B=8 满足 Knee 定义。这些结论都来自当前 Toy Lab，不能直接外推成 vLLM 或 GPU 上的固定加速倍数；其中 Cache Strategy 还带有明确的原始数据缺口。

</Note>

当前还没有覆盖：

- Multi-Head Attention、MQA 或 GQA；
- 不同长度 Sequence 的 Padding、Mask 与动态退出；
- GPU Kernel、显存带宽、Kernel Launch 与同步；
- Continuous Batching、PagedAttention 与 Scheduler；
- Client Concurrency、Queue、TTFT、TPOT、P99 与真实 Token Throughput。

## 11. Gate M：补完最小机制

### 11.1 M1：Batch Size 曲线（已完成）

**Question：** 固定 Sequence Length 后，增加 Batch 能把多少固定开销摊薄，何时开始出现收益收窄？

**Prediction：** `B` 增大时总 Positions/s 先提高，但不会保持线性；Batch Wall Time 和单 Sequence 可见的完成时间可能同时增长。

**Controlled Action：**

- 固定 `T=128`、维度、dtype、权重、随机种子和单线程 BLAS；
- 只扫描 `B∈{1,2,4,8}`；
- 每个 `B` 先做正确性检查，再做 10 次 Warm-up 和 30 次计时；
- 随机化各个 `B` 的运行顺序，减少温度和频率漂移造成的顺序效应；
- 同时记录 Batch Wall Time、`wall_time / B`、Positions/s、P50/P95 和全部原始样本。

**Artifact：** 扩展 `benchmark.py` 和测试；生成独立 CSV、汇总表、延迟曲线与吞吐曲线，不覆盖 M0 的原始数据。

**Result：** 240 条原始样本完整；Positions/s 的相邻增幅为 61.27%、36.19% 和 -0.21%，按低于 10% 的定义得到 <code>Knee: B=8</code>。完整证据见 [Batch Size Knee 分析](/labs/kv-cache-batch/view/results/batch-size-scan/knee-analysis.md/)。

**Acceptance：**

1. 所有 `B` 的输出都与逐 Sequence Oracle 数值等价，且 Batch 间没有状态泄漏；
2. 能指出吞吐收益是否开始收窄；如果扫描范围内没有拐点，明确写成 `Not reached`；
3. 能区分“总吞吐提高”和“单请求更快”，不再把二者都叫做 Batch 加速。

**Next Decision：** 不继续追求更大的 `B` 或更大的倍数；先关闭 P0 的记录缺口，再进入 Head 维与 KV 容量。

### 11.2 P0：关闭 NumPy 语义记录缺口

当前 [`examples/numpy_array_semantics.py`](/labs/kv-cache-batch/view/examples/numpy_array_semantics.py/) 已经包含 Binding、浅复制、基础切片、Advanced Indexing、<code>swapaxes</code> 和 <code>concatenate</code>。缺少的不是更多示例代码，而是以下可审查记录：

1. 运行前写出每段代码的 Shape、是否共享内存和修改是否传播；
2. 保存实际输出，并逐项标记预测是否成立；
3. 至少解释一个预测错误，或主动构造一个错误假设再用输出推翻；
4. 把 View/Copy/Stride/Allocation 分别映射回 Attention 和 Dynamic KV Cache。

**Acceptance：** 不看代码也能说明哪些操作只改变 View、哪些会分配新 Buffer，以及它们为什么会影响 Benchmark；记录完成后把 P0 标记为 Completed。

### 11.3 M2：MHA/GQA 与 KV 容量

把状态扩展为：

```text
Q: [B, H_q,  T, D_head]
K: [B, H_kv, T, D_head]
V: [B, H_kv, T, D_head]
```

**Question：** Query Head 共享 K/V Head 后，语义映射和 Cache 容量怎样变化？

**Prediction：** 固定 `H_q=8` 时，GQA 的 `H_kv=2` 只需要 MHA `H_kv=8` 的四分之一逻辑 K/V 字节；它减少状态量，但不能凭这个 Toy 实验断言真实模型质量或 GPU 延迟也按四倍变化。

**Controlled Action：**

- 实现 MHA：`H_q=H_kv=8`；
- 实现 GQA：`H_q=8, H_kv=2`；
- 显式检查 `H_q % H_kv == 0`，按 `query_head // group_size` 映射到 KV Head；
- 构造各 Head 数据不同的用例，防止错误映射被相同输入掩盖；
- 对 MHA/GQA 分别检查 No Cache 与 Cache 的逐位置等价性；
- 记录 `K.nbytes + V.nbytes`，与下式逐项对照：

$$
S_{KV}=2\times B\times H_{kv}\times T\times D_{head}\times\text{dtype bytes}.
$$

**Artifact：** Multi-Head/GQA 实现、映射测试、容量 CSV 和 MHA/GQA 对照表。

**Acceptance：** 正确性、非法 Head 配置、Batch 隔离和容量公式四类测试全部通过；实测字节数精确匹配公式。

<Note title="Toy Lab 的停止线" class="title-underline">

M2 完成后停止为 NumPy 项目增加完整 MLP、Transformer Layer、Tokenizer 或 Sampling。它们会扩大实现，却不会让当前系统产生请求排队、动态 Batch 或 KV Block 压力。下一项能力必须在真实 Serving 中学习。

## 13. Gate E：受控 Serving 实验

### 13.1 S2：只改变 Input Length

**Question：** 没有 Prefix Reuse 时，Prompt 变长怎样改变 TTFT、Decode 节奏和 KV 占用？

**Prediction：** Input Length 增大时 TTFT 和初始 KV Usage 上升；TPOT 也可能因每步读取更长历史而上升，但具体趋势必须实测。

**Protocol：** 固定 Output Length 为 64、Client Concurrency 为 1、Scheduler 配置与随机种子，只扫描 `input_len∈{128,512,2048}`。使用随机且不共享早期前缀的 Prompt；保存实际 token 数，防止字符长度冒充 token 长度。

**Artifact：** 每请求 TTFT/TPOT/ITL/E2E、Prompt/Output Token 数、服务端 KV Usage 时间线、3 轮原始结果和汇总曲线。

**Acceptance：** 每条曲线能回到单请求记录；如果 Backend 没有 KV 指标，只能报告客户端趋势，KV 因果标记为 `Inconclusive`。

### 13.2 S3：只改变 Client Concurrency

**Question：** 更多未完成请求怎样把系统从低利用率推向饱和？

**Prediction：** Output Token Throughput 先增长后趋缓；越过饱和点后，P95/P99 TTFT、TPOT 或 E2E 仍可能继续恶化。

**Protocol：** 固定 Input/Output Length、请求总数、到达模式、模型和 Scheduler 配置，只扫描 `max_concurrency∈{1,2,4,8,16}`。记录 Request Throughput 与 Input/Output Token Throughput，不用单一“吞吐”混写三者。

**Artifact：** 吞吐—并发曲线、TTFT/TPOT/E2E 的 P50/P95/P99、Running/Waiting 和 KV Usage 时间线。

**Acceptance：** 预先把“饱和拐点”定义为：并发提高一级后，Output Token Throughput 增幅低于 10%，同时至少一个 P95 延迟指标恶化超过 20%。如果扫描范围内不满足，就写 `Not reached`，不要选最大并发充当拐点。

### 13.3 S4：分开扫描 Scheduler Budget

**Question：** 配置的调度上限是否真的约束了每轮执行，还是工作负载根本没有填满它？

**Prediction：** 增大 `max_num_seqs` 或 `max_num_batched_tokens` 只有在 Waiting Requests 足够、KV 容量允许且 Backend 真正实现参数时才可能提高吞吐。

**Protocol：**

1. 选用 S3 中能稳定产生 Waiting Requests 的负载；
2. 从 [`Engine Arguments`](https://docs.vllm.ai/en/latest/configuration/engine_args/) 和本机日志记录默认值；
3. 固定 Token Budget，只扫描 `max_num_seqs`；
4. 恢复 `max_num_seqs`，再单独扫描 `max_num_batched_tokens`；
5. 每个服务端配置都重启服务并保存完整命令，客户端负载不变。

**Artifact：** “配置上限—实际 Running/Waiting/KV—客户端指标”对照表和每次启动日志。

**Acceptance：** 能证明实验负载触及了被扫描的约束；若参数被 Backend 忽略、没有可观测指标或负载未填满预算，结果必须是 `Inconclusive`，而不是“调大参数无效”。

### 13.4 S5：Mixed Prefill/Decode 与 Chunked Prefill

**Question：** 一个长 Prompt 的 Prefill 到达时，正在 Decode 的短请求会不会出现 ITL 尖峰？

**Prediction：** 长 Prefill 与 Decode 竞争执行预算时，短请求的 ITL 时间线会出现可对齐的异常；若当前 Backend 支持并实际启用 Chunked Prefill，尖峰可能减弱或被拆散。

**Protocol：**

- 让一组 `input=128, output=128` 的短请求持续 Decode；
- 在稳定区间注入一个 `input=2048, output=32` 的长请求；
- 客户端与服务端统一时钟基准，保存每个流式 token 和长请求到达的时间；
- 先观察默认配置；Capability Matrix 确认支持后，才进行 Chunked Prefill on/off 对照；
- 除该开关外不改变其他负载和 Scheduler 参数。

**Artifact：** 一张对齐 Long Prefill Arrival、短请求 ITL、Running/Waiting、Token Budget 与 KV Usage 的时间线，以及至少 3 次复跑。

**Acceptance：** 尖峰必须能在复跑中重现并与长请求到达对齐；只有开关被确认生效时，才能把两组差异归因到 Chunked Prefill。

### 13.5 S6：Prefix Reuse

**Question：** 在总输入长度相同的情况下，共享前缀能否降低重复 Prefill 工作？

**Prediction：** 共享足够长的早期前缀并发生 Cache Hit 时，TTFT 应低于随机前缀；Output 阶段不应被描述成相同幅度的优化。

**Protocol：** 固定总 Input/Output Length、请求数、并发和 Scheduler 参数，对比“共享 512-token 前缀”和“前 512 token 随机化”两组请求。若本机 `bench serve --help` 提供 `--random-prefix-len`，优先用它生成固定前缀；否则保存两组自定义 JSONL。每组使用独立的 Warm-up/Cache 状态，保存实际 Prompt Token；只有 Capability Matrix 确认 Prefix Caching 和命中指标可用时才做因果比较。

**Artifact：** Prefix Query/Hit 指标、TTFT 分布、两组原始请求以及 Cache 状态准备步骤。

**Acceptance：** 总长度和输出长度匹配，命中指标证明实验组发生复用；只有 TTFT 改善却没有命中证据时，结论停留在相关性。

<Note title="实验顺序不能交换的原因" class="title-underline">

S2 先隔离输入长度，S3 再制造并发饱和，S4 才能验证调度上限；S5 和 S6 会主动改变请求之间的干扰或复用关系，因此放在基线之后。否则每组结果都同时改变多个机制，无法知道是哪一个变量起作用。

</Note>

## 14. Gate R：用源码关闭因果链

### 14.1 R0：固定实际版本，不追最新版目录

源码阅读从 S0 记录的 vLLM Core 与 Metal Plugin 版本出发。官方 [Architecture Overview](https://docs.vllm.ai/en/latest/design/arch_overview/)只作为地图，不能用最新版文件路径代替本机实际执行代码。

选择 S3 的饱和运行或 S5 的 Mixed Workload，沿着一条真实请求追踪：

```text
API request admission
  -> request / sequence state
  -> scheduler token budget and selection
  -> KV cache lookup / allocate / grow / free
  -> model runner execution
  -> output, finish or cancel
```

**必须回答的问题：**

1. 请求在什么条件下从 Waiting 进入 Running？
2. Prefill 与 Decode token 怎样消耗同一轮预算？
3. KV Block 在何处分配、追加、复用和释放？
4. `max_num_seqs` 与 `max_num_batched_tokens` 在什么分支被读取？
5. 一次完成或取消怎样改变下一轮可运行集合？
6. Metal Plugin 在哪一层替换或限制 Core 的 Model Runner、Kernel 或指标？

**Artifact：** 固定 Commit、入口函数、关键调用链、请求状态机、四条以上不变量，以及源码位置和实测时间线的对应表。只摘录必要片段，其余使用文件与行号链接。

**Acceptance：** 能用源码解释一个已经复现的指标变化，同时列出至少一个仍然成立的替代解释。源码阅读本身不算完成，必须回到实验做一次验证性改动或复跑。
